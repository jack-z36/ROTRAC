# ADR-0014：换手适配模块以 support 包承载并增设独立标准适配节点

- 状态：Accepted
- 日期：2026-10-15
- 范围：`teleoperation_support/` 换手支撑包、22 DoF 标准适配节点、A20/A25/A26 门禁

## 背景

换手架构要把 HandProfile 与 HandAdapter 落成可替换模块，但落点被成文约束两面夹住：Spec D1 与 CONTEXT 术语表把"求解、关节映射"锁为重定向节点**内部职责**，不是独立系统节点；A20/A25/A26 门禁（ENFORCED）精确锁定生产 composition 节点与 `src/` 顶层目录 allowlist。同时团队 22 DoF 规范要求在重定向与控制之间增加一个双向维度转换点。这个转换点与适配能力放在哪一层，票据 7.2 列为文档无法单独裁决的 D1：包内抽象零门禁改动但保不住"换手零修改"，per-hand 支撑包集合干净但必须修订成文约束。

## 备选方案

1. **全部做成现有业务包内部的抽象**（接口与 O10 实现留在 `hand_retargeting` / 控制包内）：门禁与术语零改动；代价是业务包继续持有 O10 专属事实，"中段零 O10 痕迹"验收不可能达成，换手必然修改业务包内部代码，"换手只改少数模块"的承诺从结构上破产。
2. **按手新增顶层业务节点或组合层**：模块物理上最直观；代价是违背术语表"求解、关节映射是重定向节点内部职责"的成文表述，须同时修订 A20/A25/A26 三道门禁与 Spec D1 模块清单，且节点数量随手增长，把纯数据变换抬升为进程边界。

## 裁定

1. HandProfile/HandAdapter 抽象与各手实现作为 `teleoperation_support/` 下的 support 包承载（接口包、`omnihand_o10_*` 实现包、既有硬件 adapter 包），沿用 `o10_contracts` / `o10_model_assets` 的"support 包提供能力、业务节点注入依赖"模式；求解与关节映射仍留在重定向节点内部。
2. 唯一进入数据流的新节点是 22 DoF 标准适配节点（`hand_standard_adapter_node`）：它只做原生维度 ↔ 22 DoF（未激活关节填 NaN）的纯双向数据转换，不做求解、不持安全状态；引入它的原因是统一 22 DoF 观测面必须同时服务录制/回放/可视化与控制，而双向转换放进任一业务包都会让该包感知对方维度。
3. A20/A25/A26 门禁按"新增 support 包 + 该标准适配节点"同步修订；support 包不得演化为 utils/common 依赖汇（A17）。

## 后果

- 换手 = 新增 support 包 + per-hand 配置 + HandAdapter 实现，业务包算法零修改（票据 07 零修改承诺的结构前提成立）。
- 代价：标准适配节点给链路增加一跳序列化与一个常驻进程（时延与运维面增加）；它是新架构中唯一被允许进入数据流的新节点，不得夹带业务逻辑。
- 风险：门禁修订滞后则 `test_A20/A25/A26` 直接失败；support 包若开始堆积跨主题的通用工具会撞上 A17，每个包必须绑定单一能力主题。
