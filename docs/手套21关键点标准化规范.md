# 手套 21 关键点标准化规范

> 新会话为何需要本文：公司统一的手部关键点命名规范、Rokoko 到标准格式的映射策略、未来换手套时的扩展约定——这些决策锁定了手套层的接口边界，是 `rokoko_hand_receiver_node` 改造和未来 `xsens_hand_receiver_node` 等新手套集成的唯一参考。本文是 Spec 阶段的设计决策记录，代码实施前必读。
>
> 设计状态：**Spec 锁定，待实施**（2026-10-15；随 hand-swap 票 01 对抗评审澄清单位与非有限值边界）

## 1. 设计目标

**问题域**：当前系统直接使用 Rokoko 手套的原生命名（`leftThumbProximal`），导致：
1. 命名不符合公司标准（应为 `THUMB_CMC`）
2. 未来换其他品牌手套时，下游节点需要适配不同命名
3. 缺少统一的手套无关接口层

**解决方案**：
- 定义公司统一的 21 关键点命名标准
- 每个手套 receiver 负责将原生格式映射到标准格式
- 下游 `hand_retargeting_node` 只依赖标准格式，对手套品牌无感知

## 2. 公司 21 关键点标准

### 2.1 标准命名表

公司标准定义 21 个手部关键点（空间位置点，每个包含 position + orientation）：

| 索引 | 标准名称 | 解剖学含义 |
|-----|---------|-----------|
| 0 | WRIST | 手腕 |
| 1 | THUMB_CMC | 拇指腕掌关节 |
| 2 | THUMB_MCP | 拇指掌指关节 |
| 3 | THUMB_IP | 拇指指间关节 |
| 4 | THUMB_TIP | 拇指指尖 |
| 5 | INDEX_FINGER_MCP | 食指掌指关节 |
| 6 | INDEX_FINGER_PIP | 食指近端指间关节 |
| 7 | INDEX_FINGER_DIP | 食指远端指间关节 |
| 8 | INDEX_FINGER_TIP | 食指指尖 |
| 9 | MIDDLE_FINGER_MCP | 中指掌指关节 |
| 10 | MIDDLE_FINGER_PIP | 中指近端指间关节 |
| 11 | MIDDLE_FINGER_DIP | 中指远端指间关节 |
| 12 | MIDDLE_FINGER_TIP | 中指指尖 |
| 13 | RING_FINGER_MCP | 无名指掌指关节 |
| 14 | RING_FINGER_PIP | 无名指近端指间关节 |
| 15 | RING_FINGER_DIP | 无名指远端指间关节 |
| 16 | RING_FINGER_TIP | 无名指指尖 |
| 17 | PINKY_MCP | 小指掌指关节 |
| 18 | PINKY_PIP | 小指近端指间关节 |
| 19 | PINKY_DIP | 小指远端指间关节 |
| 20 | PINKY_TIP | 小指指尖 |

**命名规则**：
- 大写蛇形命名（SCREAMING_SNAKE_CASE）
- 手指名称：THUMB / INDEX_FINGER / MIDDLE_FINGER / RING_FINGER / PINKY
- 关节缩写：CMC (腕掌) / MCP (掌指) / IP (指间) / PIP (近端指间) / DIP (远端指间)

### 2.2 语义约定

**关键点性质**：
- 每个关键点是**空间位置点**（3D position + orientation），不是关节角度
- 命名是**规范约定**，不强制精确的解剖学定义或坐标系
- 各个手套供应商可以按自己的理解提供这 21 个点的数据

**坐标系约定**：
- 公司标准**不规定统一坐标系**
- 每个手套 receiver 直接透传手套原生坐标系
- 下游 `hand_retargeting_node` 会构造自己的掌坐标系，对输入坐标系无假设
- "透传"只覆盖刚体变换——**尺度与单位不属于透传范围**：位置强制 SI 米制（非米制手套由 receiver 负责换算），receiver 发布期做量纲自检（如腕–中指 MCP 距离合理区间），越界告警
- `header.frame_id` 必须携带手套轴约定标签（如 `rokoko_glove`），下游不得对轴朝向做隐式假设

**强制约束**：
- 所有手套必须输出**恰好 21 个关键点**
- 顺序必须符合上表（索引 0-20）
- 名称必须使用标准命名（不能自定义）

## 3. ROS 消息定义

### 3.1 StandardHandKeypoints.msg

消息类型：`teleoperation_interfaces/msg/StandardHandKeypoints`

```msg
# 公司标准 21 关键点手部数据
# Package: teleoperation_support/ros_interfaces

std_msgs/Header header
  # stamp: 手套数据接收时间（本机 ROS 时间）
  # frame_id: 手套坐标系标签（如 "rokoko_world_y_up_z_forward"）

string[21] names
  # 必须按索引顺序填充标准名称（WRIST, THUMB_CMC, ...）
  # 每次发布都填完整数组，保证自描述性

geometry_msgs/Pose[21] poses
  # position: 3D 位置（单位由手套定义，通常为米）
  # orientation: 四元数姿态 (x, y, z, w)
  # 缺失点用 NaN 标记：position=(NaN, NaN, NaN), orientation=(0,0,0,1)
```

**放置位置**：`src/teleoperation_support/ros_interfaces/msg/StandardHandKeypoints.msg`

### 3.2 Topic 规范

| Topic 名称 | 消息类型 | 频率 | 说明 |
|-----------|---------|------|------|
| `/mocap/left_hand/pose` | `StandardHandKeypoints` | 100Hz | 左手标准格式 |
| `/mocap/right_hand/pose` | `StandardHandKeypoints` | 100Hz | 右手标准格式 |

**历史兼容**：
- Topic 名称保持不变（`/mocap/{side}_hand/pose`）
- 消息类型从 `geometry_msgs/PoseArray` 改为 `StandardHandKeypoints`
- 下游节点需要同步更新订阅类型

## 4. Rokoko 到标准格式的映射

### 4.1 Rokoko 原生格式

Rokoko 手套输出 21 个关键点，原生命名（命名与 21 点完整性由本地 `rokoko_hand_receiver/core/decoder.py` 实证；UDP 14043 / JSON v3 另有官方插件 README 佐证，LZ4 压缩公开资料未覆盖、以本地实证为准）：

| 索引 | Rokoko 名称 | 示例 |
|-----|------------|------|
| 0 | Hand | `leftHand` |
| 1 | ThumbProximal | `leftThumbProximal` |
| 2 | ThumbMedial | `leftThumbMedial` |
| 3 | ThumbDistal | `leftThumbDistal` |
| 4 | ThumbTip | `leftThumbTip` |
| 5-8 | Index{Proximal,Medial,Distal,Tip} | `leftIndex...` |
| 9-12 | Middle{Proximal,Medial,Distal,Tip} | `leftMiddle...` |
| 13-16 | Ring{Proximal,Medial,Distal,Tip} | `leftRing...` |
| 17-20 | Little{Proximal,Medial,Distal,Tip} | `leftLittle...` |

- 还是应该对应 `THUMB_MCP`？

### 4.3 数据处理规则

**完整性验证**：
- 按节点名称查找（不依赖 JSON 数组顺序）
- 验证全部 21 个 Rokoko 节点存在且唯一
- 缺失或重复时拒绝整帧（计数器 + 节流日志）

**缺失点处理**：
- 如果某个关键点数据不可用（位置/姿态非有限值），该点标记为缺失
- 缺失点的 `poses[i].position` 设为 `(NaN, NaN, NaN)`
- 缺失点的 `poses[i].orientation` 设为单位四元数 `(0, 0, 0, 1)`
- `names[i]` 仍填充标准名称（保证数组长度为 21）

**坐标系透传**：
- `header.frame_id` 从 `rokoko_world_y_up_z_forward` 改为 `rokoko_glove`（更通用）
- 位置和姿态数值直接透传，不做坐标变换

**时间语义**：
- `header.stamp` = 本机接收 UDP 包的 ROS 时间
- 不使用 Rokoko 的 `source_timestamp`（单位未确认）

**保留原始格式（调试用）**：

## 5. 未来换手套的扩展策略

### 5.1 架构原则

**每个手套独立 receiver package**：
- `rokoko_hand_receiver_node` → 发布 StandardHandKeypoints
- `xsens_hand_receiver_node` → 发布 StandardHandKeypoints（未来）
- `manus_hand_receiver_node` → 发布 StandardHandKeypoints（未来）

**统一发布到相同 Topic**：
- 所有 receiver 都发布到 `/mocap/{side}_hand/pose`
- Launch 文件中同时只启动一个 receiver

### 5.2 新手套集成 Checklist

当需要集成新手套（如 Xsens）时：

1. **创建独立 package**：`xsens_hand_receiver_node`
2. **实现解析器**：解析 Xsens 原生格式（可能是 UDP/TCP/其他协议）
3. **实现映射**：将 Xsens 关键点映射到公司 21 个标准名称
   - 如果 Xsens 只有 16 个点 → 缺失的 5 个填 NaN
   - 如果 Xsens 有 25 个点 → 选择最接近的 21 个映射
4. **发布标准消息**：`StandardHandKeypoints` 到 `/mocap/{side}_hand/pose`
5. **验证下游兼容性**：确保 `hand_retargeting_node` 无需修改即可工作
6. **编写本手套的映射文档**：记录 Xsens 术语到标准名称的对应关系

### 5.3 不同数量关键点的处理

**原则**：强制 21 个点，用 NaN 填充

**示例 1**：某手套只有 16 个点（缺少拇指 CMC）
- 映射其 16 个点到标准索引
- `THUMB_CMC` 位置设为 NaN
- `names` 数组仍然 21 个

**示例 2**：某手套有 25 个点（多了手掌中心等）
- 选择最接近标准定义的 21 个点映射
- 多余的点丢弃
- 编写映射文档说明选择逻辑

## 6. 接口契约

### 6.1 手套 receiver 必须满足的约定

任何手套 receiver（当前 Rokoko，未来其他品牌）必须：

1. **发布标准消息**：
   - 类型：`StandardHandKeypoints`
   - Topic：`/mocap/{side}_hand/pose`（left/right）
   
2. **保证数组完整性**：
   - `names` 数组恰好 21 个元素
   - `poses` 数组恰好 21 个元素
   - 顺序符合标准表（索引 0-20）

3. **每次发布填充 names**：
   - 不能留空或部分填充
   - 用于下游验证和自描述

4. **缺失点标记规范**：
   - 用 NaN 标记，不用零值
   - `position=(NaN, NaN, NaN)`, `orientation=(0,0,0,1)`

5. **验证输入完整性**：
   - 按手套原生名称验证（不盲目按索引）
   - **结构性缺失**（节点不存在）或**重名** → 拒绝整帧
   - 数值**非有限**（NaN/Inf）→ 不拒帧，按条 4 该点 NaN 标记（瞬时缺失）

6. **时间语义一致**：
   - `header.stamp` = 本机接收时间
   - 用于下游 stale 判定

### 6.2 下游节点可以依赖的保证

`hand_retargeting_node` 及其他订阅者可以依赖：

1. **格式固定**：21 个点，顺序不变
2. **命名标准**：`names[i]` 符合标准命名表
3. **时间语义**：`header.stamp` 是接收时间
4. **缺失标记**：NaN 表示无效，零值表示真实数据
5. **手套无关**：不需要知道数据来自 Rokoko 还是其他手套

## 8. 设计决策记录（Grilling 结果）

以下决策已在 Spec 阶段锁定（2025-01-15，通过 grilling 方法确认）：

| 决策点 | 选择 | 理由 |
|-------|-----|------|
| Q2: 是否支持换手套 | 是 | 未来可能换其他品牌 |
| Q6: 映射放在哪里 | rokoko_receiver 内部 | 下游不感知手套品牌 |
| Q7: 映射如何配置 | 硬编码 | 映射关系固定，不需要配置文件 |
| Q9: 消息类型 | 自定义 StandardHandKeypoints | 自描述，包含 names 字段 |
| Q10: Topic 名称 | 保持 /mocap/{side}_hand/pose | 已是标准，不改 |
| Q11: 消息字段 | 最小化（header+names+poses） | 不包含 confidence 等扩展字段 |
| Q12: 新手套架构 | 每个手套独立 package | 简单直接，避免过度设计 |
| Q13: 缺失点处理 | 用 NaN 标记 | 让下游决定如何处理 |
| Q14: names 字段 | 每次都填 | 自描述性重要 |
| Q17: 坐标系 | 不管，直接透传 | retargeting 自己构造坐标系 |
| Q18: confidence 字段 | 不加 | 需要时再扩展 |
| Q19: 不同数量关键点 | 强制 21 个，NaN 填充 | 保持接口统一 |
| Q20: 输入验证 | 验证手套输出完整性 | 健壮性优先 |
| Q21: 消息放哪里 | ros_interfaces package | 复用现有 interfaces |
| Q22: 原始格式 | 保留（调试用） | 双 topic 发布 |
