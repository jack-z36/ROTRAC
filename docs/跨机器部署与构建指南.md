# 跨机器部署与构建指南

> 新会话为何需要本文：另一台电脑上的 agent 没有本机的历史上下文。本文只讲部署的“道”——每一步在证明什么、哪些信号不可信、失败时该停在哪；具体环境细节引用现有文档，不复述。

## 1. 部署边界

目标机器有全套硬件，定位是**完整替代工作站**：能跑真实 Rokoko → O10 链路，能录扭转诊断并分析。

**部署成功**定义为：

1. 软件基线构建成功，消息可 import，相关测试通过；
2. 真实链路短时冒烟通过：节点全部启动、反馈就绪、`motion_enabled=true`、无锁存故障、手能安全跟随小幅动作；
3. 完成一次扭转诊断录制，分析脚本能读出指标。

**不在部署范围**：代码如何传到另一台电脑、外部采数据 MCAP/数据集流程、Launchpad 作为必达项、票 06 的完整真机试点与标定。试点是部署之后的独立任务。

部署的产出不是“命令跑完了”，而是一组可复核的证据：`init` 输出、消息 import 结果、链路状态、`runs/twist-diag/<timestamp>/` 录制目录、`summary_left.json`。

## 2. 基线探测：先证明环境，再构建

不要假设目标机器和当前工作站一样。先探测，再决定是否继续。

**支持基线**：

| 项目 | 已验证值 |
| --- | --- |
| 操作系统 | Ubuntu 24.04 |
| ROS | ROS 2 Jazzy |
| Python | 3.12 |
| 架构 | x86_64 |
| 数值环境 | 仓库根 `.venv`（Pinocchio / NLopt / NumPy / vendor omnihand） |
| 模型资产 | 仓库根 `omnihand_o10_model/`，含 `provenance.json` |
| vendor SDK | `src/third_party/agillink_omnihand_sdk/linux/x64/ros2/jazzy/` |
| 构建 base | `scripts/workspace_paths.sh` 提供的 ASCII 路径（默认 `~/rotrac-build`） |

**最小探测**：

```bash
cd "$(git rev-parse --show-toplevel)"
lsb_release -a
ls /opt/ros
python3 --version
uname -m
test -x .venv/bin/python
.venv/bin/python -c "import pinocchio, nlopt, numpy"
test -f omnihand_o10_model/provenance.json
test -f src/third_party/agillink_omnihand_sdk/linux/x64/ros2/jazzy/setup.bash
lsusb -d a8fa:8598
```

**权限前提**：不要假设 agent 有 `sudo` 或网络。缺依赖时，先列清单（缺什么、为什么需要、建议装法），交给人决定；不要静默 `--install`，也不要跳过缺失依赖继续构建。

**不一致就停**：OS/ROS/Python/架构任一不同，先做移植评估，不要直接套命令。构建 base 必须能写成 ASCII；如果仓库路径含中文，更不能把产物放进仓库根 `build/`/`install/`。

## 3. 构建的“道”

### 两个 Python 世界

- **ROS 世界**：`/opt/ros/jazzy`，负责 `rclpy`、消息、launch、节点发现。
- **数值世界**：仓库根 `.venv`，负责 Pinocchio、NLopt、NumPy 和 vendor omnihand SDK。

两者都生效才算环境就绪。`ros2 run hand_retargeting hand_retargeting_node` 是错的——系统 Python 里没有 Pinocchio/NLopt；重定向节点必须走项目 wrapper（强制校验 `DEXHIT_COLLECTION_PREFIX` 与 `OMNIHAND_O10_MODEL_FIXTURE`，缺一即 `BLOCKED_ENV`）。这是 fail-closed，不是可以绕过的报错。

### ASCII 构建 base

仓库路径可能含中文。CMake 的 `file(STRINGS)` 会在非 ASCII 字节处拆行，导致 rosidl 接口生成失败。因此所有 colcon build/install/log/test-result 产物走 `scripts/workspace_paths.sh` 提供的 ASCII base，源仓库路径保持不变。`ROTRAC_COLCON_BASE` 可覆盖，但必须是 ASCII。

### 固定资产

`omnihand_o10_model/` 与 `src/third_party/agillink_omnihand_sdk/...` 是仓库内固定来源的资产，不是 pip 包，也不需要现场下载。`src/third_party/COLCON_IGNORE` 保证 colcon 不把 vendor 前缀识别成本仓库源码包。模型资产的 `provenance.json` 是来源与校验清单；缺失就停。

### 规范构建

```bash
source /opt/ros/jazzy/setup.bash
./scripts/init_omnihand.sh
```

如果机器上有无关 ROS 节点（f1、realsense、vive 等），先确认没有 `/rokoko_*`、`/hand_retargeting`、`/o10_*` 属于本次链路；只有在这种情况下才使用 `--allow-live-graph`。不要用它掩盖正在运行的 Rokoko/O10 节点。

手工构建骨架（仅在需要绕过 init 时）：

```bash
source /opt/ros/jazzy/setup.bash
source scripts/workspace_paths.sh
colcon --log-base "$ROTRAC_LOG_BASE" build --symlink-install \
  --build-base "$ROTRAC_BUILD_BASE" \
  --install-base "$ROTRAC_INSTALL_BASE"
source "$ROTRAC_INSTALL_BASE/setup.bash"
```

### 构建成功证明什么

证明：11 个自有包被 colcon 发现并构建；`rokoko_omnihand_msgs` 生成了 `TwistState` 等接口；基础 import 路径可用。

不证明：实体手安全、实时性、扭转参数已标定、物体能被拧动、真机链路能持续运行。

### 已知红测试（2026-10-19 基线）

`init` 目前会构建成功，但全量测试可能以非零退出：

- 5 项 `test_t10_faults`：故障注入的时序失败，单独运行同样失败。
- 1 项 `test_t10_graph::test_three_calibrated_public_replays_record_p1_p2_p3_age_and_solve_metrics`：负载下偶发；单独运行 `test_t10_graph.py` 9 项全绿。

这不代表“测试可以忽略”。这 5 项是安全故障演习：注入通信/反馈故障后，控制节点必须锁存故障并停止发新命令。规则是：

1. 记录红名单，和上面 6 项逐一比对；
2. 完全一样：在第一次上真机前，必须手动做一次故障注入确认，或把这些测试修绿，否则不能宣布部署成功；
3. 出现第 7 个红：停下，先查新问题；
4. 不要在部署时顺手改这些既有测试来“变绿”。

## 4. 真机链路的“道”

### 唯一入口与安全边界

真实链路只用仓库根 `./scripts/start_omnihand_control.sh`。它按固定顺序启动接收、重定向、HCAN Provider 和 O10 控制节点，并在业务节点之前自动启动扭转诊断录制。

当前控制契约**没有 arm/disarm 门**：反馈就绪、错误监控就绪、目标就绪且新鲜时，`motion_enabled=true`，戴着手套移动就会驱动实体手。开始前必须完成人工安全确认：手周围无障碍、无人员、无易夹线缆，随时可 Ctrl-C。不要同时点亮合成输入源和真机 Provider；合成假帧喂进真机链会直接驱动实体手。

### 先发现 HCAN，再设编号

HCAN 是 O10 的 USB-CAN 适配器。启动脚本用设备编号区分左右手，默认左手 `1`、右手 `0`，但这是历史双适配器工作站的枚举结果，不是永久真理。

先确认设备存在：

```bash
lsusb -d a8fa:8598
```

然后从单侧开始：

```bash
./scripts/start_omnihand_control.sh --sides left
```

看 Provider 日志：

- 出现 `Device 0, channel 0 opened successfully` 或 `Device 1 ...`：记下实际编号；
- 出现 `Device ID 1 exceeds device count 1`：说明只有一个适配器，用 `OMNIHAND_O10_LEFT_CANFD_DEVICE_ID=0` 重新启动；
- 编号不对时，不要改源码，也不要伪造反馈；用环境变量覆盖左右编号。

单适配器左手示例：

```bash
OMNIHAND_O10_LEFT_CANFD_DEVICE_ID=0 ./scripts/start_omnihand_control.sh --sides left
```

右侧同理使用 `OMNIHAND_O10_RIGHT_CANFD_DEVICE_ID`。首次部署建议只开 `--sides left`，确认左侧链路和状态；右侧即使硬件在位，也先按同一流程单独确认。

### 启动后看什么

另开终端：

```bash
source /opt/ros/jazzy/setup.bash
source scripts/workspace_paths.sh
source "$ROTRAC_INSTALL_BASE/setup.bash"

ros2 node list
ros2 topic hz /rokoko/left/raw_hand
ros2 topic echo /o10_control/left/state --once
ros2 topic echo /hand_retargeting/left/twist_state --once
```

`/o10_control/{side}/state` 的关键信号：`feedback_ready`、`error_monitor_ready`、`target_ready`、`target_fresh`、`fault_latched`、`motion_enabled`。只有这些条件满足且 `fault_latched=false`，才允许戴手套动作。

`twist_state` 的关键信号：`active`、`gate_aperture`、`gate_extension`、`theta_increment`、`theta_robot_cmd`、`refinement_status`、`failure_reason`。自由空间应 `active=false`；三指捏合后应 `active=true`，精修应为 `APPLIED` 或可解释的 `FALLBACK_BASELINE`。

### 停止

Ctrl-C。启动脚本会停止所有子节点，录制器收到 TERM 后关闭 MCAP。确认：

```bash
cat runs/twist-diag/<run>/metadata.json   # phase=finished
ros2 bag info runs/twist-diag/<run>/bag
ros2 node list                            # 不应残留业务节点
```

## 5. 验收的“道”

### A. 真实链路冒烟

- 节点全部可见，无旧节点残留；
- `/rokoko/{side}/raw_hand` 有稳定频率；
- `/o10_control/{side}/state` 满足 `feedback_ready`、`error_monitor_ready`、`target_ready`、`target_fresh`、`fault_latched=false`；
- `motion_enabled=true` 后，手能安全跟随小幅动作；
- 停止移动后目标变旧，系统自动暂停，不继续发新命令。

这一层证明“链路活着”，不证明扭转功能可用。

### B. 扭转诊断录制与分析

按票 06 的最小协议：1 名操作者、左手、1 个物体、3 次扭转 × 10 秒；另录 2 分钟自由空间和普通抓握/握拳负样本。每次启动都自动录制；建议扭转、自由空间、负样本分成独立 run 目录，避免事后猜时间窗。

```bash
python3 scripts/analyze_twist_diagnosis.py runs/twist-diag/<twist-run> --side left
python3 scripts/analyze_twist_diagnosis.py runs/twist-diag/<free-run> --side left --negative-window 0:120
```

判读：

- `angle_feedback.rmse_rad / mae_rad / pearson`：机器人反馈转角 vs 人手意图；
- `axis_deviation_feedback_deg.mean / max`：轴是否稳定；
- `refinement.applied_ratio / fallback_ratio / failure_reason_counts`：精修是否真的在工作；
- `negative_gate.false_trigger_rate / activation_episodes`：负样本有没有误触发。

如果 `fallback_ratio` 很高，先看 `failure_reason_counts`，不要盲目放宽参数：`limits`/`trust-region` 才考虑动边界；`axis-mismatch` 是符号/映射问题，不能用阈值掩盖；`baseline-incomplete` 先查逐指 IK。

### 安全故障确认

如果目标机器复现了那 5 项 `test_t10_faults` 红项，第一次上真机前必须做一次手动故障确认：注入一个可恢复的通信/反馈异常，观察 `/o10_control/{side}/state` 是否 `fault_latched=true` 且停止发新命令；确认后按现有流程 `clear_fault`。不能只凭“构建成功”就跳过这一步。

### 不要说的话

物体实际转角未测。没有物体位姿/ArUco/滑移测量，不能把“机器人转角跟上了”写成“物体拧成功了”。扭转参数仍是未标定试点初值；部署通过不等于功能验收通过。

## 6. 失败模式与交接

| 现象 | 最可能原因 | 动作 |
| --- | --- | --- |
| rosidl 生成失败、IDL 行被截断 | 构建路径含非 ASCII | 用 `scripts/workspace_paths.sh` 的 ASCII base；不要用仓库根 `install/` |
| `No module named pinocchio` / `nlopt` | 用了系统 Python 或 `.venv` 不完整 | 用 `.venv`；检查 `cmeel.prefix` 路径；不要混用两套 site-packages |
| `BLOCKED_ENV` | wrapper 缺 `DEXHIT_COLLECTION_PREFIX` 或 `OMNIHAND_O10_MODEL_FIXTURE` | 按规范启动入口；确认模型 fixture 有 `provenance.json` |
| `missing tip frame` / 模型错误 | 模型资产缺失或不匹配 | 停；检查 `omnihand_o10_model/` 与 `provenance.json` |
| `Device ID N exceeds device count` | HCAN 编号假设错误 | 用 `lsusb` + Provider 日志确认实际编号，设 `OMNIHAND_O10_*_CANFD_DEVICE_ID` |
| 启动脚本拒绝启动 | 旧 ROS 图仍在 | 先停旧节点；确认无误后才考虑 `--allow-live-graph` |
| 节点启动失败、缺参数 | 生产参数文件缺 `twist_*` | 用 `runs/retargeting_diag_params.yaml`；缺任一必填参数就修配置，不要给代码加默认值 |
| `theta_robot_fb_available=false` | 反馈未到、参考无效或几何无效 | 看 `/o10/{side}/joint_states` 和 `failure_reason`；不要用 0 冒充 |
| 测试红了 | 可能是已知 6 项，也可能是新问题 | 比对名单；新红就停；5 项故障红先做手动故障确认或修绿 |
| 精修一直回退 | 参数/几何/限位/轴问题 | 看 `failure_reason_counts`，一次只改一个变量，重录同场景对比 |

**不要做**：

- 不要用 `ros2 run hand_retargeting hand_retargeting_node` 绕过 wrapper；
- 不要改 O10 控制节点的硬限速、运动许可或故障语义；
- 不要在真机 Provider 运行时喂合成输入；
- 不要把 `--allow-live-graph` 当成万能开关；
- 不要只凭构建成功宣布部署成功；
- 不要为了变绿而改既有测试；
- 不要一次改四个权重后凭感觉判断；
- 不要把“机器人转角跟上”写成“物体被拧动”。

**交接**：部署完成后更新 `STATUS.md` 的真机状态；把红名单、HCAN 实际编号、启动命令和 run 目录写进票据或交接记录；如果改了参数，写回 `runs/retargeting_diag_params.yaml` 并注明未标定；最后跑 `./scripts/doc_gate.sh`，保持 error 为 0。
