## 1. ros2_control hardware_interface

### 1.1 三类硬件组件与接口签名风格

ros2_control 把物理硬件抽象为三类组件：**Actuator / Sensor / System**，分别对应 `ActuatorInterface / SensorInterface / SystemInterface`（官方定义："Hardware components represent abstraction of physical hardware in ros2_control framework"，https://control.ros.org/jazzy/doc/ros2_control/hardware_interface/doc/hardware_components_userdoc.html ）。

`SystemInterface` 的类注释明确了它的定位——"Virtual Class to implement when integrating a **complex system** into ros2_control"，典型例子是"multi-joint systems with or without sensors such as industrial or humanoid robots"（https://raw.githubusercontent.com/ros-controls/ros2_control/jazzy/hardware_interface/include/hardware_interface/system_interface.hpp ）。多关节灵巧手正落在这一类。

纯虚方法（子类必须实现）：

```cpp
// HardwareComponentInterface 基类中声明（jazzy 分支）
virtual return_type read(const rclcpp::Time & time, const rclcpp::Duration & period) = 0;
// SystemInterface 中追加
return_type write(const rclcpp::Time & time, const rclcpp::Duration & period) override = 0;
```

初始化回调由基类提供。**Jazzy 发布版的官方教程与示例代码**中，`on_init` 接收从 URDF 解析出的 `HardwareInfo`，教程原文要求子类先调父类：`hardware_interface::(Actuator|Sensor|System)Interface::on_init(info)`，然后从 `info` 解析参数、返回 `CallbackReturn::SUCCESS` 或 `CallbackReturn::ERROR`（https://control.ros.org/jazzy/doc/ros2_control/hardware_interface/doc/writing_new_hardware_component.html ）。注意：**仓库 jazzy/master 分支的头部文件已在演进**，最新代码中签名为 `virtual CallbackReturn on_init(const hardware_interface::HardwareComponentInterfaceParams & params)`（注释仍是 "Initialization of the hardware interface from data parsed from the robot's URDF"）（https://raw.githubusercontent.com/ros-controls/ros2_control/master/hardware_interface/include/hardware_interface/hardware_component_interface.hpp ）。引用 API 时需注意版本差异；语义上两者都是"把 URDF 描述喂给组件初始化"。

返回值风格：生命周期回调返回 `rclcpp_lifecycle::node_interfaces::LifecycleNodeInterface::CallbackReturn`，三值语义（源码注释原文）：

- `SUCCESS` —— "method execution was successful"；
- `FAILURE` —— "has failed and **can be called again**"（可重试）；
- `ERROR` —— "critical error has happened that should be managed in **on_error**"。

（两处来源：system_interface.hpp 与 lifecycle 文档，URL 同上；https://control.ros.org/jazzy/doc/ros2_control/hardware_interface/doc/lifecycle_of_a_hardware_component.html ）

read/write 返回 `hardware_interface::return_type`（OK / ERROR 等）。

### 1.2 生命周期

四个状态 + 对应回调（https://control.ros.org/jazzy/doc/ros2_control/hardware_interface/doc/lifecycle_of_a_hardware_component.html ）：

| 状态 | 回调 | 官方语义（引文） |
| --- | --- | --- |
| UNCONFIGURED | `on_init`, `on_cleanup` | "Hardware is only initialized, but communication is not started and no interfaces are imported into ResourceManager." |
| INACTIVE | `on_configure`, `on_deactivate` | 通信已建立；"States can be read, but command interfaces are not available." |
| ACTIVE | `on_activate` | "Power circuits of hardware are active"（如抱闸松开）；状态可读、命令可发 |
| FINALIZED | `on_shutdown` | "Ready for unloading/destruction. Allocated memory is cleaned up." |

生命周期遵循 ROS 2 node lifecycle；关键错误（`CallbackReturn::ERROR`）路由到 `on_error(previous_state)`。

文档还记录了一个已知缺口：截至 Jazzy，**INACTIVE 状态下命令接口实际仍然可用且会被写入**（文档引用 issue ros-controls/ros2_control#931），运动类接口（`HW_IF_POSITION/VELOCITY/ACCELERATION/EFFORT`）的 INACTIVE 屏蔽只在路线图上。这是"安全关键接口"尚未完成的注脚，对设计 Adapter 的安全语义有直接参考价值。

### 1.3 错误处理

官方文档（https://control.ros.org/jazzy/doc/ros2_control/hardware_interface/doc/handling_errors_during_read_write.html ）：

- 触发条件："If `hardware_interface::return_type::ERROR` is returned from `read()` or `write()` methods of a hardware_interface class, `on_error(previous_state)` method will be called"；
- "Error handling follows the node lifecycle"：`on_error` 返回 `SUCCESS` 则硬件回到 UNCONFIGURED（可重新 configure/activate）；返回 `ERROR`/`FAILURE` 则硬件进入 FINALIZED，"can not be recovered"；
- 唯一出路是"reload the complete plugin"，且文档明言"there is currently no service for this in the Controller Manager"。

即：**框架的故障恢复是保守的——致命错误后硬件组件不可原地复活**，把故障处理责任前移到组件内部的非致命路径（read/write 返回 OK 但上报降级状态等）。

### 1.4 URDF `<ros2_control>` 插件标签与 pluginlib 注册

硬件组件由 URDF 中的 `<ros2_control>` 标签声明式描述。官方 demo（ros2_control_demos example_2，原文引用，https://github.com/ros-controls/ros2_control_demos ）：

```xml
<ros2_control name="${name}" type="system">
  <hardware>
    <plugin>ros2_control_demo_example_2/DiffBotSystemHardware</plugin>
    <param name="example_param_hw_start_duration_sec">0</param>
    <param name="example_param_hw_stop_duration_sec">3.0</param>
  </hardware>
  <joint name="left_wheel_joint">
    <command_interface name="velocity"/>
    <state_interface name="position"/>
    <state_interface name="velocity"/>
  </joint>
  <!-- ... -->
</ros2_control>
```

结构要素：`name`/`type`（system|actuator|sensor）属性、`<hardware><plugin>`（插件名字符串）+ 任意 `<param>`（进 `hardware_parameters` map）、`<joint>/<sensor>/<gpio>/<transmission>` 子元素各带若干 `<command_interface>/<state_interface>`（可带 min/max/initial_value/data_type）。解析产物 `HardwareInfo` 结构（源码，https://raw.githubusercontent.com/ros-controls/ros2_control/jazzy/hardware_interface/include/hardware_interface/hardware_info.hpp ）：

```cpp
struct HardwareInfo {
  std::string name, type, group;
  unsigned int rw_rate; bool is_async; /*...*/
  std::string hardware_plugin_name;
  std::unordered_map<std::string, std::string> hardware_parameters;
  std::vector<ComponentInfo> joints;
  std::vector<MimicJoint> mimic_joints;          // URDF <mimic> 关节的解析产物
  std::vector<ComponentInfo> sensors, gpios;
  std::vector<TransmissionInfo> transmissions;
  std::string original_xml;
  std::unordered_map<std::string, joint_limits::JointLimits> limits;
  std::unordered_map<std::string, joint_limits::SoftJointLimits> soft_limits;
};
```

`ComponentInfo` 含 `name/type/is_mimic/enable_limits/command_interfaces/state_interfaces/parameters`；`InterfaceInfo` 含 `name/min/max/initial_value/data_type/size/parameters/enable_limits`（同上源码）。**即：关节名、每关节接口集合、数值限位、mimic 关节、硬件参数，全部由一份 URDF 声明式承载，解析器生成结构化 HardwareInfo 交给硬件组件。** controller_manager 侧要求 "All joints defined in the `<ros2_control>`-tag have to be present in the URDF"（https://control.ros.org/jazzy/doc/ros2_control/controller_manager/doc/userdoc.html ）。

C++ 侧插件注册（教程原文，https://control.ros.org/jazzy/doc/ros2_control/hardware_interface/doc/writing_new_hardware_component.html ）：

1. .cpp 末尾 `PLUGINLIB_EXPORT_CLASS(具体类, hardware_interface::SystemInterface)`（include `pluginlib/class_list_macros.hpp`）；
2. 插件描述文件 `<package>.xml` 中写 `<class name="包名/类名" base_class_type="hardware_interface::SystemInterface">`；
3. CMakeLists 调 `pluginlib_export_plugin_description_file(hardware_interface <package>.xml)`。

controller_manager 启动时从 `robot_description` 参数读 URDF → 解析 `<ros2_control>` → 按 `hardware_plugin_name` 经 pluginlib 动态加载组件，接口导入 ResourceManager；控制器经 ResourceManager 以 loaned handle 形式认领 state/command 接口（`loaned_state_interface.hpp`/`loaned_command_interface.hpp` 为 hardware_interface 包内头文件名，见 https://github.com/ros-controls/ros2_control/tree/jazzy/hardware_interface/include/hardware_interface ）。**controller_manager 与具体硬件零耦合：双方只共享"接口名 + double 值 + 生命周期"这个契约。**

其余组件级机制（教程同页）：

- 接口默认从 `<ros2_control>` XML 自动导出到 `joint_command_interfaces_`/`joint_state_interfaces_` 等 map，组件内用 `get_state(name)/set_state(name,value)/get_command(name)/set_command(name,value)` 读写；另可 override `export_unlisted_state_interface_descriptions()/export_unlisted_command_interface_descriptions()` 导出非关节接口；
- 可选的 `prepare_command_mode_switch()/perform_command_mode_switch()` 钩子处理命令模式切换（如位置↔速度）；
- 组件可经 `get_node()` 获得框架提供的生命周期节点发布诊断话题。

### 1.5 语义组件（semantic components）与 gripper

在裸接口之上，ros2_control 提供"语义组件"封装，目的原文是 "streamline the configuration of commonly used hardware interface"——把"认领一组接口并按语义读写"打包（https://control.ros.org/jazzy/doc/ros2_control/hardware_interface/doc/semantic_components.html ）：

- 只写基类 `semantic_components::SemanticComponentCommandInterface`，子类：`LedRgbDevice`。

### 1.6 限位即配置：joint_limits_interface

`joint_limits_interface` 包（README，https://raw.githubusercontent.com/ros-controls/ros2_control/humble/joint_limits_interface/README.md ）：

- 数据结构：`JointLimits`（position/velocity/acceleration/jerk/effort）与 `SoftJointLimits`（soft position limits、k_p、k_v，沿 PR2 安全规范）；
- 双源加载：**URDF**（position/velocity/effort + soft limits）与 **ROS 参数服务器**（覆盖/补充 acceleration/jerk/effort），且明言参数命名规范"the same used in MoveIt"；
- 强制点："is *not* used by controllers themselves... instead operates **after** the controllers have updated, in the `write()` method (or equivalent)... Enforcing limits will *overwrite* the commands set by the controllers"——按接口类型分三档实现（effort=PR2 软限位、position=改造版软限位、velocity=加速度/速度饱和）。

另注：Jazzy 官方文档中还预留 `hardware_components_initial_state` 等 CM 参数用于指定组件初始状态（https://control.ros.org/jazzy/doc/ros2_control/controller_manager/doc/userdoc.html ）。

### 1.7 同一描述切换真机/仿真硬件（mock 组件）

demo 例程用 xacro 条件参数在**同一份 URDF 内切换硬件插件**（上文 1.4 的同一 demo，`use_mock_hardware` 为真时）：

```xml
<hardware>
  <plugin>mock_components/GenericSystem</plugin>
  <param name="calculate_dynamics">true</param>
</hardware>
```

即上层（controller_manager、controllers、MoveIt）完全不感知被换掉的硬件后端——真机、mock、（第三方）Gazebo/Isaac 集成共用同一描述与同一控制器栈。

## 2. MoveIt 2：控制器与 gripper 适配层

### 2.1 三层控制器管理器

MoveIt 通过抽象基类 **MoveItControllerManager** 与底层控制器解耦，官方教程（https://moveit.picknik.ai/main/doc/examples/controller_configuration/controller_configuration_tutorial.html ）给出三条并列路线：

1. **MoveItSimpleControllerManager**——"For most use cases... sufficient if your robot controllers already provide ROS actions for FollowJointTrajectory"；通过 launch 参数 `moveit_controller_manager` 指定实现类，控制器清单以 YAML 传给 MoveGroup 节点；
2. **Ros2ControlManager**（插件包 `moveit_ros_control_interface`）——被文档称为 "the best way to interface with ros2_control"：**自动发现** ros2_control 中已加载的 controller，解析轨迹命令中的关节名并激活对应 controller，甚至"automatically switching between one and two manipulators in a joint group"；launch 中以 `moveit_manage_controllers = true` 启用；
3. 多 ros_control 实例场景用 `Ros2ControlMultiManager`。

关键解耦事实：**MoveIt 不要求 ros2_control**——任何暴露 FollowJointTrajectory / GripperCommand action 的控制器都能接入（文档："99% of users choose ros2_control"，但私有 action 亦可）。适配约定是 action 路径 `/name/action_ns`（如 `/hand_controller/gripper_action/goal`）。

### 2.2 控制器 YAML（声明式适配清单）

```yaml
controller_list:
- name: arm_controller
  action_ns: follow_joint_trajectory
  type: FollowJointTrajectory
  default: true            # 该关节集合的首选控制器
  joints: [...]            # 关联关节
  allowed_execution_duration_scaling: 1.2
  allowed_goal_duration_margin: 0.5
```

`type` 字段即动作类型（FollowJointTrajectory / GripperCommand），`joints` 声明该控制器管辖的关节集合——**"哪个动作接口管哪些关节"完全由 YAML 声明，管理器代码通用**。

### 2.3 Gripper 适配：GripperCommand 的两种手型

同一教程对 gripper 的专门约定：

- `type: GripperCommand`，同样 name/action_ns/default/joints 结构；
- **`command_joint`**："The single joint, controlling the actual state of the gripper"——单关节手；
- **`parallel: true`**："joints should be of size 2, and the command will be the sum of the two joints"——平行夹爪两指对称联动，MoveIt 把单值命令求和分发。

即 MoveIt 用两个 YAML 字段把"语义开合命令 → 具体关节拓扑"的映射做成配置，而不是让规划器理解手的机械结构。这与 SRDF 的 end-effector group 声明（见 §4.2）配合：规划针对 group，执行交给 controller_manager。

### 2.4 SRDF：把手声明为"语义组"

SRDF 补充 URDF 不能表达的语义（MoveIt 教程，https://moveit.picknik.ai/main/doc/examples/urdf_srdf/urdf_srdf_tutorial.html ）："specifies joint groups, default robot configurations, additional collision checking information, and additional transforms"：

- **Groups**：四种定义方式（关节集合/连杆集合/base-tip 链/子组组合）；
- **End-Effectors**：把一个 group 标注为某父 group（如 arm）的末端，要求末端与父组无公共连杆；
- **Group States**：命名姿态（如 HOME），存字符串 id 可复位；
- **Passive Joints**：标记不可直接控制的关节；
- **Virtual Joints / disable_collisions**：根坐标系挂接与碰撞对豁免。

加载方式（ROS 2）：`robot_description`（URDF）与 `robot_description_semantic`（SRDF）作为节点参数或 topic 注入。

## 3. Drake：执行器抽象与 SchunkWSG 适配

### 3.1 MultibodyPlant / JointActuator：拓扑+限位即模型

Drake 把"哪个关节被驱动、驱动上限多少"建模为 **JointActuator**——官方 API 文档措辞是 "mostly a simple bookkeeping structure to represent an actuator acting on a given Joint"（https://drake.mit.edu/doxygen_cxx/classdrake_1_1multibody_1_1_joint_actuator.html ）：

- `effort_limit()`：默认 +∞（无限制），必须严格为正（否则抛异常）；单位随关节类型（转动 N·m / 平动 N）；`set_effort_limit()` 可改；
- `input_start()` / `num_inputs()`：该执行器在整机驱动向量 `u` 中的偏移与长度（= 关节 nv）；`get_actuation_vector(u)/set_actuation_vector(u_act, u)` 读写；
- 名称全模型唯一，由 `MultibodyPlant::AddJointActuator()` 强制；
- 可选内置 PD：`set_controller_gains()` 后 plant 暴露 `get_actuation_input_port()`（前馈力矩）与 `get_desired_state_input_port()`（期望状态）。

**即：手的关键契约（DOF、驱动向量布局、力矩限位）由模型描述承载，plant 的执行接口是按执行器索引切片的一个 double 向量。**

### 3.2 SchunkWSG 适配层：driver 是"接线"，controller 是"翻译"

Drake 为 Schunk WSG 50 两指夹爪提供了三件套（源码 https://github.com/RobotLocomotion/drake/tree/master/manipulation/schunk_wsg ）：

**（a）SchunkWsgDriver（实机接线描述）**——struct 字段 `pid_gains{7200., 0., 5.}`（注释解释 p≈皮带弹性模量、d≈齿轮箱黏性摩擦、"The i term is nonphysical"）、`lcm_bus`；类注释原文："specifies how to wire up Drake systems between an LCM interface and the actuation input ports of a MultibodyPlant. **This simulates the role that driver software and control cabinets would take in real life.**" 它在 `SCHUNK_WSG_STATUS` 通道发布状态、在 `SCHUNK_WSG_COMMAND` 通道订阅命令（https://raw.githubusercontent.com/RobotLocomotion/drake/master/manipulation/schunk_wsg/schunk_wsg_driver.h ）。

**（b）SchunkWsgPositionController（语义命令翻译）**（https://raw.githubusercontent.com/RobotLocomotion/drake/master/manipulation/schunk_wsg/schunk_wsg_position_controller.h ）：

- 输入端口：`desired_position`（**两指间距**语义）、`force_limit`（可不接，用构造默认）、`state`（手指状态）；输出端口：`generalized_force`、`grip_force`；
- 内部用 `StateInterpolatorWithDiscreteDerivative` 从位置命令估计期望速度；
- 几何翻译：命令 q_d 是两指间距，机械约束 `-q₀ = q₁`，硬件内部跟踪 `-q₀ = q₁ = q_d/2`——**"语义命令 → 每指关节目标"的 2:1 映射写在 controller 文档里**；
- 力饱和：`-f₀+f₁ = sat(kp·(q_d + q₀ − q₁) + kd·(v_d + v₀ − v₁))`，sat 界于 ±force_limit；
- 对称约束：内部约束控制器 `f₀+f₁ = −kp_c(q₀+q₁) − kd_c(v₀+v₀)` 保持手指对称，"The expectation is that kp_constraint ≫ kp_command"；
- 构造默认：`time_step=0.05`（注释：匹配 wsg 固件更新率）、kp=200、kd=5、kp_constraint=2000、default_force_limit=40。

**（c）仿真/实机同构**：同一 PositionController 既接到 MultibodyPlant（仿真）也接到 LCM 实机通道（driver），上层例程（manipulation_station 等）不区分。

可提炼的 Drake 模式：**模型(MultibodyPlant/URDF/MJCF 前身) 承载拓扑与限位；driver 承载传输协议；controller 承载"产品语义命令（开度/力限）→ 关节级目标"的手特定几何与增益**。三者可独立替换。

## 4. "Hand Profile" 概念的业界形态（横向简述）

### 4.1 URDF/SRDF（ROS 系声明式基准）

- URDF `<joint>` 规范（http://wiki.ros.org/urdf/XML/joint ）：类型 revolute/continuous/prismatic/fixed/floating/planar；`<limit lower upper effort velocity>`（revolute/prismatic 必填）；`<safety_controller soft_lower_limit soft_upper_limit ...>`；
- **`<mimic joint multiplier offset>`**（ROS Groovy 引入）：被 mimicking 关节的值 = `multiplier * other_joint_value + offset`——**仅线性耦合**。ros2_control 的 HardwareInfo 直接解析出 `mimic_joints` 列表（§1.4 源码）；dex-retargeting 则提供 `MimicJointKinematicAdaptor` 在运动学层处理 mimic 关节（https://github.com/dexsuite/dex-retargeting ，retargeting_config.py import 语句可见）。对本项目的**非线性**被动耦合多项式，两个基准都只覆盖线性特例——多项式耦合属自定义扩展，需自选承载文件（MJCF tendon 亦为线性系数组合，见下）；
- SRDF（§2.4）：group/end-effector/group states/passive joints——把手组织为可规划语义单元。

### 4.2 MJCF / MuJoCo Menagerie：模型即配置

Menagerie 是 Google DeepMind 策展的高质量 MuJoCo 模型库，自述使命与分级（README，https://raw.githubusercontent.com/google-deepmind/mujoco_menagerie/main/README.md ）："a collection of high-quality models for the MuJoCo physics engine, curated by Google DeepMind"；质量四级 A+（"Values are the product of proper system identification"）到 C（"Conditionally stable, can be significantly improved"）。手类模型清单含 Allegro(16 DOF)、Shadow E3M5(24 DOF)、LEAP(16 DOF)、Robotiq、DEX-EE、Sharpa Wave、Aero Hand 等。

Shadow Hand 模型（https://raw.githubusercontent.com/google-deepmind/mujoco_menagerie/main/shadow_hand/right_hand.xml ）示范了 MJCF 承载手 profile 的全部要素：

- 关节拓扑+限位：`<joint axis="0 0 -1" range="-1.0472 1.0472"/>`（thbase）、proximal `range="-0.261799 1.5708"` 等；
- 驱动参数：`<position name="rh_A_THJ5" class="thumb" .../>` 带 `kp`、`ctrlrange`、`forcerange`；
- **耦合**：fixed tendon 把被动弯曲耦合为主关节线性组合——`<fixed name="rh_FFJ0"><joint joint="rh_FFJ2" coef="1"/><joint joint="rh_FFJ1" coef="1"/></fixed>`（FF/MF/RF/LF 四指同构）——与本项目 MJCF 主动-被动耦合多项式同源，但 tendon 也是线性系数；
- defaults/class 继承树（`right_hand → thumb → thbase/...`）实现按指分组的参数复用。

### 4.3 dex-retargeting：重定向侧的 per-hand YAML profile

dex-retargeting（源自 AnyTeleop，与本项目"中段重定向"同类工作）把每只手的重定向配置做成 YAML + dataclass（源码 `RetargetingConfig`，https://raw.githubusercontent.com/dexsuite/dex-retargeting/main/src/dex_retargeting/retargeting_config.py ）：

```python
@dataclass
class RetargetingConfig:
    type: str                      # "vector" | "position" | "dexpilot"
    urdf_path: str                 # 目标手的 URDF 资产路径
    add_dummy_free_joint: bool = False
    target_link_human_indices: Optional[np.ndarray] = None   # 人手关键点↔机器人 link 对应
    wrist_link_name: ...
    target_link_names: ...         # position 型
    target_origin_link_names / target_task_link_names: ...   # vector 型
    finger_tip_link_names: ...     # dexpilot 型
    scaling_factor: float = 1.0    # 例注释："Allegro is 1.6 times larger than normal human hand"
    normal_delta / huber_delta: 优化器鲁棒参数
    project_dist: float = 0.03 / escape_dist: float = 0.05   # DexPilot 投影/逃逸阈值
    has_joint_limits: bool = True
    ignore_mimic_joint: bool = False
    low_pass_alpha: float = 0.1
```

加载与构建：`RetargetingConfig.load_from_file(config_path).build()`（官方示例 `show_realtime_retargeting.py`），配置按 `(robot_name, retargeting_type, hand_type)` 三元组组织为文件（`get_default_config_path(robot_name, retargeting_type, hand_type)`）。**换一只手 = 换一份 YAML（内含 URDF 路径、link 对应表、缩放、滤波、mimic 策略），优化器代码不动。**

### 4.4 LEAP Hand：代码内 conventions 的"反例"（profile 写在代码里）

LEAP 官方 API 的 `leap_hand_utils.py`（https://github.com/leap-hand/LEAP_Hand_API ，文件 `python/leap_hand_utils/leap_hand_utils.py`）是一个完整但**写死在代码里**的手 profile 微缩样本：

- 体现（embodiment）约定注释：LEAPhand（实机，"180 for the motor is actual zero"）、LEAPsim（"allegro-like zero positions"）、one_range（RL 用 [-1,1]）、allegro；
- 16 关节限位常量数组：`sim_min = np.array([-1.047, -0.314, -0.506, -0.366, ...])`（四指×4 关节，每 4 项一指）；`sim_max = np.array([1.047, 2.23, 1.885, 2.042, ...])`；
- `angle_safety_clip(joints)`："Safety clips all joints so nothing unsafe can happen. Highly recommend using this before commanding"；
- 约定转换：LEAPhand↔LEAPsim 就是 ±3.14159 偏移；`allegro_to_LEAPhand(joints, teleop=False)` 中带 `if teleop: ret_joints[12] = joints[12] + 0.2; ret_joints[14] = joints[14] - 0.2`——**遥操作模式下对特定指关节（12/14）的专调补偿**，与本项目"拇指专调参数"同类；
- ROS 节点（`ros2_module/scripts/leaphand_node.py`）在边界上同时接受三种约定的话题（`_receive_pose/_receive_allegro/_receive_ones`），并暴露 `leap_position/leap_velocity/leap_effort/leap_pos_vel_eff` 服务取数——驱动节点负责把多种输入归一化到内部表示。

### 4.5 robosuite：Gripper/HardModel 基类 + 字符串工厂

robosuite（https://github.com/ARISE-Initiative/robosuite ）的末端执行器层（源码 `robosuite/models/grippers/`）：

- 基类 `GripperModel(MujocoXMLModel)`（`gripper_model.py`）：约定钩子 `format_action(action)`（动作语义翻译）、属性 `naming_prefix/speed/dof`、`_important_sites/_important_geoms/_important_sensors`（把"抓手要点"暴露给仿真与抓取检测）；XML 资产与 Python 类成对；
- `gripper_factory(name, idn)`：按字符串名查 `GRIPPER_MAPPING` 字典实例化（"String based method of initializing grippers"，`gripper_factory.py`）；
- 内置模型除平行爪（panda/robotiq/xarm…）外还有灵巧手 `inspire_hands.py`、`fourier_hands.py`、`jaco_three_finger_gripper.py` 等——**"一款手 = 一个 XML + 一个子类 + 注册表一行"**。

### 4.6 Isaac Lab：执行器组与 ActuatorBaseCfg

Isaac Lab 把执行器抽象为"同模型驱动的一组关节"（官方概念页 https://isaac-sim.github.io/IsaacLab/main/source/overview/core-concepts/actuators.html ）：

- 两类模型：**Implicit**（物理引擎内建弹簧阻尼，力矩直通）/ **Explicit**（用户模型先算力矩再按电机能力 clip）；
- 显式模型代表 `IdealPDActuator`：`τ = clip(kp(q_d−q) + kd(q̇_d−q̇) + τ_ff, ±γ·τ_motor,max)`（γ 为减速比）；
- **Actuator group**："a set of actuated joints on an articulation that are using the same actuator model"——同一 Articulation 可按指/按关节类型分多个组；
- 注意事项：显式模型需调 armature 保稳定；"policies trained with implicit actuators may not transfer" 到显式模型。

具体 Cfg 字段（`joint_names_expr`、`effort_limit_sim`、`stiffness/damping` 等在 API 文档 `isaaclab.actuators`，本次页面未逐一展开——**字段级细节未在本报告核实**）。

## 5. 共性模式提炼

跨框架比对得到六条反复出现的通用手法（每条附出处框架）：

1. **声明式描述承载"手是什么"，代码只实现"怎么驱动"**。拓扑、DOF、限位、资产路径全部在描述文件（URDF `<ros2_control>`+`<limit>`+`<mimic>` / MJCF `range`+`ctrlrange` / dex-retargeting YAML / MoveIt controller YAML / SRDF group）；硬件后端代码（SystemInterface 子类、LCM driver、GripperModel 子类）只实现协议与时序。（ros2_control §1.4、MJCF §4.2、dex-retargeting §4.3）
2. **插件名即配置项 + 运行时注册表**。`<plugin>` 字符串经 pluginlib 动态加载；robosuite `GRIPPER_MAPPING` 字典；MoveIt `moveit_controller_manager` 参数选实现类。共同点：**选择硬件后端是数据，不是代码分支**。（§1.4、§4.5、§2.1）
3. **能力以"接口集合"暴露，消费者按名认领**。ros2_control 的 state/command interface + ResourceManager loaned handles；Drake 的 actuation 向量按 JointActuator 偏移切片；LEAP ROS 节点按服务名暴露 pos/vel/eff。上层不持有硬件类型，只持有接口名与维度。（§1.4、§3.1、§4.4）
4. **统一生命周期 + 保守故障语义**。UNCONFIGURED→INACTIVE→ACTIVE→FINALIZED，FAILURE 可重试、ERROR 走 on_error 且不可逆（仅能重载插件）；Drake 虽无显式状态机，但 driver/controller 分离使故障域隔离在同一层。共同点：**激活/停用是显式协议步骤，故障恢复不自动"复活"硬件**。（§1.2、§1.3、§3.2）
5. **语义命令与关节命令分层翻译**。夹爪"开度"→ 每指 q_d/2 + 力饱和 + 对称约束（Drake）；"闭合"action → command_joint 或 parallel 求和（MoveIt）；人手关键点 → 关节角（dex-retargeting，含 scaling_factor 与 low_pass_alpha）。手特定几何与增益放在**翻译层**，不放进传输层。（§3.2、§2.3、§4.3）
6. **mock/仿真与实机同构**。`mock_components/GenericSystem` 由同一 URDF 的 xacro 参数切换（§1.7）；Drake 同一 controller 接 MultibodyPlant 或 LCM 实机（§3.2）。测试栈与真机栈共享全部上层代码。

配置与代码的职责边界（汇总表）：

| 载体 | 业界普遍放入的内容 | 对应本项目概念 |
| --- | --- | --- |
| URDF/MJCF 模型 | 关节拓扑、限位、几何、（线性）耦合、执行器 ctrlrange/forcerange | 模型资产 |
| 描述内 `<ros2_control>` 标签 / YAML | 插件名、硬件参数、控制器清单、动作类型、关节集合 | 硬件后端选择 |
| 专用 YAML | 限位覆盖（URDF+参数双源）、重定向参数（link 对应/缩放/滤波）、控制器增益 | HandProfile 参数 |
| 代码 | 传输协议、时序、生命周期、故障处理、优化/控制律、约定转换 | HandAdapter 实现 |
